01 / Product baseline

Decisions we have made

First delivery

A working local prototype for candidates and advisers, using fictional profiles and vacancies with real processing. English first, covering varied military backgrounds through described experience.

Start with reviewed structured facts, then add automated extraction to the same journey. Stage 2 completes the AI prototype.

Human control

Advisers approve vacancies before publication. Candidates confirm inferred skills, correct their profile, inspect gaps, and rerun matching. Employers remain responsible for hiring decisions.

Recommendations are unranked and evidence-backed. There is no blended suitability score, automated rejection, or hiring decision.

  1. Experience
  2. Reviewed profile
  3. Approved vacancy
  4. Evidence comparison
  5. Correction
  6. Updated result

Source of requirements: proposal.pdf and the decisions recorded here. The agreed clarification extends “potential match, mandatory gap” to unmet negotiable requirements, even when they are not learnable.

Deferred from the initial delivery: employer accounts, automated applications, vacancy scraping, scanned-document OCR, and broad multilingual support. EU hosting and real-data processing terms must be resolved before the pilot.

02 / System design

Clear ownership across the system

Application components and boundaries
ComponentResponsibility
React applicationCandidate and adviser screens, review forms, evidence display, progress, and accessible recovery states. TypeScript and Vite.
Go APIAuthentication, authorization, validation, domain commands, database writes, and public/internal APIs. Thin HTTP handlers over services and repositories; pgx, sqlc, and SQL migrations.
Go activity workerDeterministic matching and evaluation persistence, reusing the backend domain code. A separate process from the same backend codebase.
Python Temporal workerWorkflow orchestration, local parsing/redaction, Gemini extraction, mapping suggestions, embeddings, and explanations. Python submits artifacts through the authenticated Go internal API.
PostgreSQL + pgvectorProfiles, versions, approved requirements, evidence links, embeddings, evaluations, reviews, processing status, and transactional outbox.
Private document storageOriginal documents and processing artifacts. Private filesystem adapter locally; production object storage behind the same interface.
Temporal serviceDurable execution, activity scheduling, retries, and execution history. Owns execution state; PostgreSQL owns application and human-review state.

Contracts and local runtime

One repository with separated frontend, Go backend, Python worker, and shared contract packages. Group backend code by profiles, vacancies, matching, reviews, access, and processing. Share OpenAPI and JSON Schema contracts, generated language types, and runtime validation. Public routes use /api/v1; internal processing endpoints require distinct service authentication. Version Temporal payloads explicitly.

Run locally through Docker Compose with persistent Temporal development storage, PostgreSQL, private document storage, and a local OIDC identity provider with seeded candidate/adviser accounts. React proxies application requests to Go. Temporal and Postgres are sufficient for the initial workload; no additional broker, cache, or search service is planned.

Durable data flow

  1. The Go API commits an operation and an outbox entry together, then returns 202 Accepted with an operation identifier.
  2. A Go dispatcher starts Temporal with a stable operation-based workflow ID. Repeated delivery recognizes an existing execution; database idempotency outlives workflow-history retention.
  3. Python orchestrates bounded activities. Go activities evaluate frozen inputs; Python activities access source artifacts and submit results through the internal API.
  4. Activities persist idempotent outputs. The frontend polls application status and retrieves results from Go, independently of the Temporal UI.

Evidence and versions

Keep documents/source segments, extracted assertions, candidate corrections, profile versions, vacancy versions/requirements, evaluations/findings, reviews/overrides/acknowledgements, and processing runs as distinct records.

Freeze the profile, vacancy, policy, taxonomy, model/prompt versions, and evaluation time for every comparison. Preserve provenance for candidate-added experience. Historical records remain immutable during retention, but remain subject to deletion.

Privacy boundaries

Parse and redact locally; obtain candidate approval of sanitized text before model calls, including embeddings. Redaction is fallible and requires review. Exclude raw service/discharge records.

Temporal receives opaque references, including activity results. Keep CV text, snippets, model output, credentials, and sensitive exception details out of histories, search attributes, and logs.

Recovery and lifecycle rules

  • Use separate bounded workflows for document preparation, profile extraction, vacancy extraction, matching, explanations, and deletion. Human approvals live in PostgreSQL and start the next operation.
  • Use bounded activity timeouts, three attempts with exponential backoff for external AI calls, and limited concurrency. Invalid input and authorization errors are non-retryable.
  • Keep workflow code deterministic; perform file, network, and model operations in activities. Deduplicate persisted outputs and reuse completed artifacts. Repeated provider billing after an ambiguous failure cannot be ruled out.
  • Make exhausted retries visible with a safe retry path. Support bounded graceful shutdown and workflow replay/version compatibility.
  • A completed old evaluation cannot replace a newer profile’s current result. Acknowledgements and overrides attach to exact evaluations; material changes require reevaluation.
  • Deletion blocks access/new processing, cancels pending work, and removes sources and derived artifacts. Retrying work checks deletion state and cannot recreate removed data.
03 / Matching contract

Rules and evidence determine the result

Apply this precedence once inputs are ready. The initial threshold is evidence for at least two-thirds of approved core requirements; tune it through a versioned policy after pilot evaluation.

Result precedence, evaluated from top to bottom
ConditionResult
Core evidence below two-thirdsNo suitable match
Threshold reached; an unmet mandatory gate is fixed and non-learnableSkills match, blocked by fixed requirement
Threshold reached; unmet mandatory gates are learnable or negotiablePotential match, mandatory gap
Threshold reached; no mandatory gate is unmetPotential match — prominently show any unverified requirements
  • Mandatory states are met, not met, unverified. Unknown information never counts as failure. Core evidence distinguishes stated, inferred awaiting confirmation, and not found; inferred skills count only after confirmation.
  • Store learnability independently from gate type (negotiable, fixed, unclear). An unmet negotiable requirement stays unmet until explicitly resolved. Show every mandatory gap even when one determines the headline result.
  • Advisers resolve ambiguous gates, duplicate/compound clauses, and requirements with alternatives before publication. Each approved core requirement counts once; “Python or Go” is one alternative requirement. A vacancy with no core requirements requires review.
  • Similarity and occupation crosswalks suggest connections, not proof of an individual skill. Preserve unresolved skills and their evidence. Do not assume military codes from different countries are equivalent.
  • Restricted experience stays self-attested and counts as neither met nor absent. Military training does not become a civilian certificate. Unknown duration or equivalence remains unverified. Career breaks are not penalized; matching uses years worked rather than career-gap dates.
  • Exclude protected identity information from skill matching. Ask eligibility questions only when declared by a vacancy and evaluate them separately. Flag proxy wording to the vacancy reviewer rather than applying it as a filter.
  • Evaluate every approved vacancy in the prototype catalogue. Use exact vector search for suggested skill connections. Display unranked results with status filters and stable ordering.
  • Only show a catalogue-wide no-match conclusion after the frozen vacancy set has been evaluated successfully. Processing failure means unavailable/incomplete, not unsuitable.
  • The evidence table is the canonical explanation. Gemini summarizes completed findings; validate schemas, references, and consistency, falling back to deterministic text. Citation validation alone does not prove semantic correctness; sample explanations for human review.
  • Adviser overrides preserve the machine evaluation and add a separately reasoned recommendation. Corrections to underlying facts create a new version and rerun.
04 / Delivery checklist

Build in complete, verifiable stages

Each stage includes its frontend, API, persistence, and applicable worker behavior. Sequence is governed by acceptance gates, not promised calendar dates. Progress counts verified steps equally; it is not an estimate of effort or time remaining.

01 — Working matching corePlanned · First complete candidate/adviser journey

Build a useful product with manually supplied structured facts, real matching, and durable execution. Three fictional candidates include two plausible matches and one correctly returning no suitable match.

  • Establish repository boundaries and local development

    Separate frontend, Go API/activity worker, Python workflows, and contracts. Add Compose, migrations, environment examples, startup/seed commands, and health/readiness checks.

  • Define versioned interfaces and domain records

    Implement OpenAPI/JSON Schema contracts, generated types, validation, consistent error shapes, and the evidence/version records described above.

  • Implement candidate and adviser access

    Configure local OIDC, seeded accounts, server-side authorization, candidate isolation, and assigned-adviser access. Keep service credentials separate.

  • Create and review structured candidate profiles

    Support roles, skills, tools, qualifications, languages, and duration. Record provenance, confirmations/rejections, and timestamped corrections without rewriting sources.

  • Create, review, and publish structured vacancies

    Capture source clauses, mandatory/core/desirable requirements, AND/OR relationships, learnability, and gate type. Resolve ambiguities before publishing immutable versions.

  • Implement the deterministic Go matching policy

    Cover the four result states, threshold boundaries, distinct evidence states, gap precedence, and the negotiated-gate clarification. Preserve findings for every requirement.

  • Connect matching through Temporal and the outbox

    Commit operation/outbox together, start workflows with stable IDs, schedule Go matching activities from Python, persist idempotent results, and expose processing status.

  • Build evidence results and correction/rerun screens

    Show mandatory readiness separately from core skills, expand clause/snippet evidence, render deterministic explanations, and support unranked filtering and historical results.

  • Establish independently specified fictional examples

    Use three candidates and enough vacancies to exercise all four states. Define expected requirement findings and verify that a profile correction changes the appropriate result.

  • Verify the complete matching-core journey

    Pass applicable formatting, lint, type, unit, integration, contract, migration, worker, and build checks. Demonstrate real UI → API → persistence → Temporal → result behavior.

Exit gate: Candidates and advisers can produce, inspect, correct, and reproduce real comparisons. All four states have independent expected examples; no scripted results or unverified jobs.
02 — Working AI prototypePlanned · Depends on stage 1

Add automated preparation and extraction to the established evidence and review workflow. This stage completes the agreed local AI prototype.

  • Prepare text PDFs and pasted text

    Validate and bound inputs, store private documents, parse locally, and create stable source segments. Give encrypted, scanned, or unsupported files a pasted-text/manual-entry recovery path.

  • Redact locally and review sanitized input

    Exclude sensitive content before external calls. Require candidate approval of sanitized text; apply that boundary to embeddings as well. Never ingest raw service/discharge records.

  • Integrate Gemini behind a provider interface

    Implement schema-validated extraction/explanation calls and embeddings. Explicitly configure and record model/prompt versions, bounded timeouts, three-attempt backoff, and concurrency limits.

  • Extract source-linked candidate assertions

    Validate source references and distinguish stated facts from proposed inferences. Add review screens for confirmations, rejections, and corrections that feed versioned profiles.

  • Import versioned ESCO/O*NET data and mappings

    Preserve dataset releases, attribution, and crosswalk provenance; verify release compatibility. Retain unresolved skills instead of treating missing taxonomy coverage as absent experience.

  • Suggest transferable skills with evidence

    Use embeddings and occupation mappings to propose connections, require confirmation for inferred transfers, and keep professional qualifications and restricted claims distinct.

  • Extract draft vacancy requirements for advisers

    Link clauses, classify requirements, flag proxy wording, and expose coverage/ambiguity review. Publication remains an explicit adviser action.

  • Evaluate the complete approved catalogue

    Freeze vacancy versions for each run; compare every approved vacancy and use exact vector retrieval for skill suggestions. Do not exclude opportunities through approximate retrieval.

  • Generate and check plain-language explanations

    Generate only from completed findings; check evidence references and consistency. Preserve deterministic fallback text and perform sampled human checks for unsupported claims.

  • Verify the uploaded-document journey

    Run fictional CV → sanitized approval → extraction → profile review → approved vacancy → comparison → correction → rerun. Rejecting an inferred skill must update the result correctly.

Exit gate: Fictional uploads complete the real AI journey. The no-match case is correct, all claims are traceable, and extraction failures never become unsuitable-candidate outcomes.
03 — Adviser and reliability completionPlanned · Depends on stage 2

Complete review operations and prove the system behaves correctly when processing is interrupted, repeated, or overtaken by a correction.

  • Complete the adviser review workspace

    Provide review queues, evidence inspection, reasoned recommendation overrides, and correction/rerun actions. Preserve the original machine evaluation.

  • Implement warn-and-proceed acknowledgements

    Show every mandatory gap before proceeding. Allow correction/rerun and log acknowledgement of remaining gaps against the exact evaluation; avoid ineffective advice for fixed gaps.

  • Prevent stale results from replacing current results

    Freeze input versions, separate historical/current evaluations, reject stale publication updates, and require new acknowledgement after material input changes.

  • Complete retry, failure, and shutdown behavior

    Deduplicate results, reuse completed artifacts, classify permanent/transient errors, show exhausted failures with safe retries, and support bounded graceful shutdown and restart recovery.

  • Verify workflow evolution and cross-language payloads

    Test Go/Python serialization contracts, workflow replay against saved histories, and compatible activity/workflow version changes.

  • Implement deletion across sources and derived data

    Block access and processing first, cancel pending work, remove documents/assertions/embeddings/explanations, and prevent in-flight retries from recreating deleted data.

  • Make operations diagnosable without sensitive logs

    Record request/job correlation, attempts, timing, safe failure codes, outbox age, provider latency/cost, and worker health. Keep sensitive payloads out of Temporal and logs.

  • Complete accessible review and recovery states

    Adapt the supplied design reference for readable forms and evidence tables. Cover keyboard/screen reader, mobile, low bandwidth, loading, empty, validation, unauthorized, and unavailable states.

  • Pass resilience and isolation acceptance checks

    Exercise crash-after-commit, duplicate delivery, worker restart, provider outage, partial completion, stale correction, deletion races, and unauthorized candidate/adviser/service access.

Exit gate: Recovery, permissions, review history, and user-visible status are verified across the full stack. A shared fictional-data demonstration can now be prepared.
04 — Pilot readiness and evaluationPlanned · Depends on stage 3 and external reviews

Prepare for the proposal’s indicative pilot of 20–30 volunteers and 30–50 civilian vacancies. Real personal data is admitted only after every go-live condition passes.

  • Agree pilot scope, data terms, and vacancy supply

    Confirm the NSPA sponsor/adviser workflow, volunteer participation, curated or NSPA-supplied vacancies, responsibilities, and provider/data-processing terms.

  • Deploy and harden the EU runtime

    Select the hosting provider and production identity/storage configuration. Separate environments and secrets, restrict access, protect uploads/endpoints, configure backups, and verify restoration.

  • Complete consent, retention, and candidate notices

    Implement approved notices, deletion/retention controls, and auditable consent. Keep optional demographic monitoring outside matching and independent of service/employer-sharing access.

  • Complete external legal and data-protection review

    Have the combined DPIA/impact assessment reviewed by counsel and NSPA’s data-protection contact. Validate current requirements and approve candidate notice/consent before go-live.

  • Pass the external accessibility audit

    Target WCAG 2.2 AA, verify keyboard/screen-reader and mobile behavior, and resolve all blocking findings before real participants use the system.

  • Pass fairness and explanation review

    Run identity swaps and same-facts plain/non-native rewrites through the full pipeline. Require unchanged result states and no unsupported claims in sampled explanations; resolve failures first.

  • Pass the security review

    Include prompt injection in CV/vacancy text, authorization, uploads, credentials, protected data boundaries, logs, and Temporal payloads. Resolve blocking findings.

  • Establish monitoring and incident procedures

    Monitor failures, queue/outbox delays, provider use, correction patterns, and audit events. Document migrations, rollback, restoration, incident response, and sampled adviser review.

  • Run and evaluate the pilot

    Conduct weekly log/adviser reviews. Measure relevance, mandatory-requirement detection, time to three useful roles, fairness stability, false positives, unsupported claims, and correction patterns.

Go-live gate: Approved impact/data-protection review, candidate notice/consent, external accessibility audit without blockers, fairness stability, sampled explanations without unsupported claims, and security review. Any failed condition blocks real-data deployment.

Pilot targets remain assumptions: 80% relevant roles, 95% mandatory requirements detected, 50% shorter median shortlist time, and 100% unchanged result states under both perturbations. The cohort is too small for broad effectiveness claims.

05 — Employer access and expansionPlanned · Depends on pilot findings

Extend the verified candidate/adviser system while preserving consent, evidence, and the separation of eligibility from skills.

  • Add employer-specific sharing and revocation

    Require separate opt-in per employer, restrict the shared evidence projection, test revocation, and never condition candidate service access on sharing consent.

  • Build the unranked employer evidence view

    Show consented evidence and named gaps without a suitability score or automatic rejection. For negotiable-gate sharing, show the gate and skills evidence, never nationality.

  • Add the vacancy-author workflow

    Let authors respond to flagged wording and maintain requirements through the approved publication/versioning process. Preserve an auditable history of changes.

  • Extend language coverage after evaluation

    Add selected languages with appropriate extraction, terminology, translation, accessible presentation, and full-pipeline fairness/quality checks.

  • Add validated integrations and measured scaling

    Choose integrations from pilot needs. Change retrieval/indexing or infrastructure only with measured performance and recall checks; reevaluate model and taxonomy upgrades before release.

  • Verify expansion without weakening the core

    Pass employer consent/isolation/revocation tests and the relevant language, model, taxonomy, contract, migration, reliability, and end-to-end regression suites.

Exit gate: Employer access is consented and revocable; each added language or integration has its own verified behavior and regression evidence.
05 / Definition of done

What must be true before a step is complete

Behavior and evidence

  • Normal and failure paths work across every affected component.
  • Thresholds, overlapping/unknown/negotiable gates, AND/OR requirements, restricted experience, and qualification distinctions are covered.
  • Invalid citations, rejected inferences, unresolved mappings, and changed input versions are exercised.
  • Fairness checks cover the complete extraction-to-result pipeline.

Engineering checks

  • Frontend formatting, lint, type checking, unit tests, and production build.
  • Backend formatting, lint/static/type checks, unit and integration tests, and build.
  • Worker retry, failure, idempotency, shutdown, and replay tests.
  • Applicable database migration and API/cross-language contract checks.
  • Documentation, environment examples, operational instructions, and this checklist updated.

Follow AGENTS.md: work on a feature/fix/chore branch, preserve unrelated changes, run all affected checks before merging, use focused commits, and merge completed work with a non-fast-forward merge before deleting the feature branch. Never mark shells, placeholders, or unverified jobs complete.
